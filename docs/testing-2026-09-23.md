# Manual Validation — Backend-Driven Scene Hydration & Sensor Tiers (2026-09-23)

Manual test plan for the change set that fixes the "white background / no selected ship" and
"Jax alone with no asteroids" defects reported after completing the first mission.

**Scope of change:** 763 insertions / 72 deletions across 27 files.

---

## What changed (context for the tester)

Four distinct root causes were fixed:

1. **Scene was hard-wired to `first-target`.** The exterior scene always resolved the
   first-target mission plugin, so `generic-exploration` was unreachable. The scene now
   derives its mission from navigation state.
2. **The only world query was mission- and character-scoped.** After the first mission's
   asteroids were mined the query returned nothing. A new mission-agnostic, owner-agnostic
   proximity sweep now hydrates the scene from the backend.
3. **Overlay close discarded navigation identity.** Closing an overlay navigated with no
   state, so downstream queries went out as `unknown-player` / `unknown-character`.
4. **Empty backend results silently became invented asteroids.** The client fabricated
   5–20 random asteroids and could persist them back to the server.

Two supporting changes:

- **Sensor-array tier now drives detection range** (T1 = 100 km … T20 = 150,000,000 km),
  transcribed from `docs/Sensor Array Master Progression Table.md`.
- **km-space was rescaled to match render space.** `DEFAULT_CLUSTER_SPREAD_KM` went
  5,000 → 20. Previously a body's persisted `positionKm` was drawn from an _independent_
  random ±5,000 km while it rendered 6–20 km away — a ~250× disagreement that meant
  persisted bodies could never match a render-space query.

> **The database wipe removes the single biggest risk in this plan.** Pre-wipe, any body
> persisted at the old ±5,000 km spread would sit outside the new ~100 km tier-1 radius and
> silently fail to render, which is indistinguishable from a broken query. Starting clean
> means every body you see was written under the new scale, so zero contacts always means
> _genuinely zero contacts_.

## Pre-flight

1. Confirm the database wipe is complete (no players, characters, ships, or celestial bodies).
2. Start the backend on `localhost:3000`.
3. Run `npm start`.
4. Open DevTools and keep two panels in view for the whole session:
   - **Console**
   - **Network → WS → Frames**

### Observation hooks used throughout

| Hook                                        | Where                                                | What it tells you                                                      |
| ------------------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- |
| Debug drawer → **World** group              | Dev-mode "Debug" button, top-right of exterior scene | `ASTEROIDS // <count> / <targeted> / <hovered> / <signature>`          |
| `ShipExterior local bodies sweep complete.` | Console                                              | `{ contacts, detectionRangeKm, centerKm }`                             |
| `celestial-body-list-request`               | WS Frames                                            | The actual query payload — the most valuable single check in this plan |
| `ShipExterior local bodies sweep failed.`   | Console                                              | Backend returned `success: false`                                      |
| `fetchActiveShip: timed out…`               | Console                                              | The 5s ship-hydration guard fired                                      |

## Phase 1 — Build the baseline state

These scenarios must run first: they create the player, character, ship, and mission
progress that every later scenario depends on.

### Scenario 1 — Account and character creation

**Why first:** nothing else can run until a character and ship exist.

1. Register a new player account.
2. Create a character.
3. Land on the character list.

**Expect**

- Character row renders with a portrait (or silhouette fallback).
- Join button reads **"Start Game"** (or equivalent new-character label) — _not_ "Join Game
  in Progress", since no mission progress exists yet.

---

### Scenario 2 — First mission: full cold-boot onboarding

**Why here:** this is both a regression guard _and_ the only way to produce the
completed-mission state Phase 2 needs. The scripted onboarding path was deliberately left
unchanged, so this should behave exactly as it did before the change.

1. Join with the brand-new character.
2. Walk the complete onboarding flow: scan → target → mine / launch → completion.

**Expect**

- Routes through `opening-cold-boot`.
- Deterministic seeded asteroids appear.
- Objectives advance normally and the mission reaches **completed**.

**Watch for**

- I removed an RNG draw from the asteroid generator, so seeded asteroid **`y` positions
  differ from pre-change builds** for the same seed. Forward determinism is preserved: the
  same seed must produce the same layout every time. Re-entering with the same seed and
  getting a _different_ layout is a real bug.
- Newly persisted bodies now use the corrected 1:1 km scale. Spot-check one body's stored
  `positionKm` against the ship's `positionKm` — the difference should be on the order of
  **6–20 km**, not thousands.

---

### Scenario 3 — In-progress resume (optional, needs a second character)

**Why here:** exercises the third routing branch. Requires a character left _partway_
through the first mission, so create a second character and stop mid-mission.

1. Create a second character and begin the first mission.
2. Log out partway through, then log back in and join.

**Expect**

- Routes to `ship-exterior-view` + `opening-cold-boot-scan` + `left:game-main`.
- Ship is hydrated at its **real** spatial position, not a `(0,0,0)` placeholder.
- Previously-scanned asteroids retain their scanned state.

## Phase 2 — The reported defects

Run these against the character that completed the first mission in Scenario 2.

### Scenario 4 — Login after first mission completed ⭐ _primary defect_

**This is the originally reported bug.**

1. Log out, then log back in with the completed-mission character.
2. Click **Join Game in Progress**.

**Expect**

- URL contains all three outlets: `ship-exterior-view` (primary), `left:game-main`,
  `right:mission-board`.
- URL does **not** contain `opening-cold-boot`.
- Header reads `ACTIVE SHIP: <ship name>` — **not** "No ship selected".
- Background is dark, not white.

**Red flags**

- White background or "No ship selected" → ship hydration on the completed path regressed.
- A noticeable hang on the character list before navigating → the ship fetch is timing out;
  check the console for `fetchActiveShip: timed out`.

---

### Scenario 5 — Close the mission board ⭐ _second reported symptom_

**This is the "Jax alone with no asteroids" report, and the highest-value check in the plan.**

1. From the end state of Scenario 4, click the mission board's **close** button.

**Expect**

- You land on the ship exterior scene; `right:mission-board` is gone, `left:game-main` is
  retained.
- A `celestial-body-list-request` fires. **Inspect the payload in WS Frames:**
  - `distanceKm: 100` (tier 1)
  - **no** `missionId` field
  - **no** `createdByCharacterId` field
  - `positionKm` matches the ship's actual position
  - `playerName` is the **real** player name
- Asteroids render if the backend returned any.

**Red flags**

- `playerName: "unknown-player"` or `unknown-character` in the payload → the overlay-close
  identity fix regressed.
- `missionId` present → mission-driven plugin resolution regressed.

## Phase 3 — New behavior

### Scenario 6 — Backend-only rule: no invented asteroids ⭐ _key regression check_

**Verifies the app stopped fabricating contacts.**

> **Do not use flight to get out of range.** Ship position is not persisted and the sweep
> does not re-run while you fly (see _Known limitations_ below), so flying away cannot put
> you outside the seeded cluster for the purposes of this check. Use a fresh character.

1. Create a **new character** that has never run a mission or mined, so no celestial bodies
   exist within 100 km of its starter ship. (Alternatively, relocate the Scenario 2 bodies
   in the database so they fall outside the ship's 100 km radius.)
2. Enter the exterior scene.

**Expect**

- Debug drawer shows `ASTEROIDS // 0 / ...`.
- A dark overlay reads **"No contacts in range"** with guidance about traveling further or
  upgrading sensors.
- Console: `sweep complete. { contacts: 0, ... }`.

**Red flag:** asteroids appearing with **no** corresponding bodies in the
`celestial-body-list-response`. Previously the client invented 5–20 random asteroids here
and could persist them back to the server. If you see that, the no-synthetic-seed rule has
broken.

---

### Scenario 7 — Sensor tier drives detection range

1. With a **tier 1** sensor array, note `distanceKm` in `celestial-body-list-request`
   → expect **100**.
2. Change the ship's sensor array to **tier 3** in the backend, reload, re-enter the scene
   → expect **750**.
3. Optionally **tier 5** → expect **7,500**.

**Expect**

- `distanceKm` tracks the tier table and console `detectionRangeKm` matches.
- More distant bodies become visible as the tier rises.

**Also check:** a ship with **no** sensor array must fall back to 100 km — not `0`,
not `undefined`.

---

### Scenario 8 — No active ship

Exercises one of the new empty states.

1. Reach the exterior scene with a character that owns **no ships** (or make the backend
   return an empty ship list).

**Expect**

- Dark **"No active ship"** overlay directing the player to the hangar.
- Not a white void, and not a crash.

### Scenario 9 — Hangar entry path

1. Navigate to **Ship Hangar** → **View Exterior** for a ship.
2. Round-trip: exterior → ship specs → back to exterior.

**Expect**

- Scanned asteroid state persists across the round trip.
- Target lock remains available.
- Navigation identity stays intact (check a WS frame for the real player name).

## Phase 4 — Failure injection

Run these last: they require deliberately breaking the backend.

### Scenario 10 — Backend unreachable / sweep failure

> Stopping the backend verifies transport-failure safety, but it does not currently settle
> the pending sweep because `listCelestialBodies()` has no response timeout. To verify the
> unavailable overlay and application warning, make the backend return an explicit failed
> response.

1. Make `celestial-body-list-request` return `success: false`.
2. Enter the exterior scene.

**Expect**

- **"Sensor sweep unavailable"** overlay.
- Console warning: `ShipExterior local bodies sweep failed.`
- Critically: **no fabricated asteroids** filling the gap.

**Transport-failure spot-check:** stop the backend and enter the scene. XHR polling
`ERR_CONNECTION_REFUSED` / `xhr poll error` messages are expected, and no asteroids may be
fabricated. The unavailable overlay is not expected until the sweep receives a response or
gains a client-side timeout.

---

### Scenario 11 — Ship-fetch timeout guard

Covers a latent bug found and fixed during implementation.

> **Automation is preferred for this scenario.** Silently dropping one Socket.IO event is
> difficult with an unmodified live backend. The focused Vitest test stubs
> `listShipsByOwner` without invoking its callback, advances fake time to exactly 5 seconds,
> and verifies the timeout warning and navigation result. Run:
>
> `npm run test:spec -- src/app/services/mission-navigation/mission-navigation.service.vitest.ts`

**Optional manual test**

1. Make the backend **silently drop** `ship-list-by-owner-request` — no response at all.
2. Log in and join with the completed-mission character.

**Expect**

- After ~5 seconds you navigate anyway.
- Console warning: `fetchActiveShip: timed out waiting for ship list response`.
- You land in the scene showing the **"No active ship"** state.

**Before this fix you would hang on the character list forever with no feedback.** That is
precisely what this guards against.

## Manual validation outcomes

The manual pass closed two gaps that could not be verified against the real backend by
automated tests:

1. **Mission-agnostic queries work against the real server.** Scenario 5 confirmed the WS
   request uses the real player identity and omits `missionId` and
   `createdByCharacterId`, and the backend returns local celestial bodies.

2. **The backend agrees with the rescaled km space.** Scenario 2 confirmed a freshly
   persisted body's `positionKm`, and Scenarios 6 and 7 confirmed empty-range behavior and
   sensor-tier detection ranges against real data.

## Known limitations (out of scope for this change)

Discovered during the 2026-09-23 manual pass. Neither is a regression from this change —
both pre-date it — but this change made them visible, so they are recorded here to avoid
being re-reported as sweep defects.

1. **Ship position is not persisted across sessions.** The flight controller tracks
   position and calls `commitTrackedLocation` at each checkpoint, but the handler in
   `ship-scene-context.ts` only updates local scene state — nothing is emitted to the
   server. After a logout/login the ship reverts to its last backend-known position, so the
   original cluster reappears close to the ship.

   The `ship-upsert-request` contract declares only `inventory`, `damageProfile`, and
   `ownership` under its `ship` patch; there is no declared `spatial`/`positionKm` field and
   no other position/move/travel event in `openapi.yaml`. Persisting position therefore
   requires a **contract decision from the backend team**, not a frontend-only fix.

2. **The local-bodies sweep does not re-run during flight.** `loadLocalCelestialBodies()`
   is reached only from cold-boot seeding, so travelling within a session never pulls in
   newly in-range contacts. Existing contacts correctly shrink with distance, which can
   make flight appear to work.

   **Symptom to expect:** flying toward empty space yields no new asteroids and no "No
   contacts in range" overlay, because the scene still holds the original sweep's results.

3. **The local-bodies sweep has no response timeout.** An explicit failed
   `celestial-body-list-response` produces the "Sensor sweep unavailable" state, but a
   transport refusal or silently dropped response leaves the sweep pending indefinitely.
   Scenario 10 confirmed that this state does not fabricate asteroids, but adding a
   client-side timeout remains a follow-up.
